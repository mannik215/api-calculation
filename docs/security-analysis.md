
# Анализ безопасности Calculator API

## 1. Цель анализа

Целью анализа является оценка безопасности разработанного Calculator API, его зависимостей, Docker-образа и процесса CI/CD.

В рамках анализа выполняются:

- статический анализ исходного кода;
- анализ сторонних Python-зависимостей;
- анализ Docker-образа;
- анализ результатов работы средств безопасности;
- ручной анализ архитектуры приложения;
- выявление потенциальных слабых мест;
- разработка и внедрение мер повышения безопасности.

Проверки безопасности интегрированы непосредственно в Jenkins CI/CD pipeline и выполняются до развёртывания новой версии приложения.

## 2. Используемые средства безопасности

В проекте используются бесплатные инструменты с открытым исходным кодом.

### 2.1. Semgrep Community Edition

Semgrep применяется в качестве средства статического анализа исходного кода (SAST — Static Application Security Testing).

Инструмент позволяет выявлять потенциально небезопасные конструкции, включая:

- использование `eval()` и `exec()`;
- небезопасное выполнение системных команд;
- потенциальные инъекции;
- использование некоторых небезопасных функций;
- известные небезопасные шаблоны программирования.

Semgrep запускается автоматически Jenkins до сборки и развёртывания приложения.

### 2.2. pip-audit

pip-audit используется для анализа сторонних Python-зависимостей (SCA — Software Composition Analysis).

Инструмент проверяет зависимости, перечисленные в `requirements.txt`, и сопоставляет их версии с базами известных уязвимостей.

Это позволяет обнаруживать случаи, когда собственный код приложения не содержит уязвимости, однако используемая сторонняя библиотека имеет известную проблему безопасности.

### 2.3. Trivy

Trivy используется для анализа готового Docker-образа.

Проверяются:

- системные пакеты базового Linux-образа;
- установленные Python-пакеты;
- известные CVE;
- уровни критичности найденных уязвимостей.

Trivy запускается после сборки Docker-образа, но до его развёртывания.

Результат анализа дополнительно сохраняется в формате JSON в файле `trivy-report.json`. Файл сохраняется Jenkins в качестве артефакта сборки.

### 2.4. pytest

pytest используется для автоматической функциональной проверки приложения.

Тестирование выполняется перед security-анализом и проверяет основные функции калькулятора.

Если тесты завершаются с ошибкой, Jenkins прекращает pipeline и не выполняет сборку и развёртывание некорректной версии.

## 3. Последовательность CI/CD и проверок безопасности

Итоговая последовательность Jenkins Pipeline имеет следующий вид:

    Git push
       |
       v
    Checkout
       |
       v
    Install dependencies
       |
       v
    pytest
       |
       v
    Semgrep SAST
       |
       v
    pip-audit
       |
       v
    Generate version
       |
       v
    Docker Build
       |
       v
    Trivy Security Gate
       |
       v
    Trivy Report
       |
       v
    Deploy
       |
       v
    Health Check

Таким образом, проверка безопасности выполняется до развёртывания новой версии.

Если функциональный тест или блокирующая security-проверка завершается ошибкой, Jenkins получает статус FAILURE, а последующие этапы, включая Deploy, не выполняются.

## 4. Результаты функционального тестирования

Перед анализом безопасности выполняются автоматические тесты Calculator API.

В ходе контрольной сборки были успешно проверены:

- сложение;
- вычитание;
- умножение;
- деление;
- обработка деления на ноль;
- обработка неизвестной операции.

Jenkins получил результат:

    6 passed

Таким образом, перед выполнением security-проверок была подтверждена базовая функциональная корректность приложения.

## 5. Результаты анализа Semgrep

Для исходного кода приложения был выполнен статический анализ Semgrep Community Edition.

Получен результат:

    Rules run: 290
    Findings: 0

Semgrep не обнаружил совпадений с использованным набором известных небезопасных шаблонов.

В частности, код Calculator API не использует динамическое выполнение пользовательских данных через `eval()` или `exec()`, не формирует системные команды на основе пользовательского ввода и не выполняет SQL-запросы.

При этом отсутствие findings не является гарантией полного отсутствия уязвимостей. Semgrep работает на основе набора статических правил и не способен выявить все логические и архитектурные проблемы.

Поэтому SAST используется совместно с анализом зависимостей, анализом Docker-образа и ручным анализом приложения.

## 6. Результаты анализа pip-audit

Для Python-зависимостей был выполнен анализ:

    python -m pip_audit -r requirements.txt

Получен результат:

    No known vulnerabilities found

Таким образом, на момент проведения анализа используемые версии Python-зависимостей не содержали известных pip-audit уязвимостей.

Результат является актуальным только на момент проверки, поскольку новые CVE могут публиковаться позднее.

Поэтому pip-audit интегрирован в Jenkins и выполняется при последующих сборках приложения автоматически.

## 7. Первичный анализ Docker-образа Trivy

Первоначальная проверка Docker-образа с помощью Trivy выявила:

    Total: 51
    HIGH: 51
    CRITICAL: 0

При этом Python-пакеты приложения не содержали обнаруженных HIGH/CRITICAL-уязвимостей.

Основная часть найденных проблем относилась к системным компонентам базового Debian-образа, включая:

- OpenSSL;
- util-linux;
- ncurses;
- системные библиотеки Debian.

Таким образом, анализ показал, что безопасность приложения зависит не только от собственного Python-кода и сторонних Python-библиотек, но и от базового Docker-образа.

Результаты можно представить следующим образом:

    Исходный Python-код
            |
            v
    Semgrep: 0 findings

    Python-зависимости
            |
            v
    pip-audit: 0 известных уязвимостей

    Базовый Docker image
            |
            v
    Trivy: обнаружены HIGH-уязвимости

## 8. Устранение выявленных уязвимостей Docker-образа

После анализа результатов Trivy в Dockerfile было добавлено обновление доступных системных пакетов:

    RUN apt-get update \
        && apt-get upgrade -y \
        && rm -rf /var/lib/apt/lists/*

`apt-get update` обновляет информацию о доступных пакетах.

`apt-get upgrade -y` устанавливает доступные обновления системных компонентов.

После обновления удаляются временные списки пакетов:

    rm -rf /var/lib/apt/lists/*

После внесения изменения Docker-образ был повторно собран и проанализирован.

## 9. Security Gate на основе Trivy

В Jenkins был настроен блокирующий Security Gate.

Используются параметры:

    --scanners vuln
    --severity HIGH,CRITICAL
    --ignore-unfixed
    --exit-code 1

Параметр `--severity HIGH,CRITICAL` ограничивает блокирующую проверку уязвимостями высокого и критического уровня.

Параметр `--ignore-unfixed` исключает из блокирующей проверки уязвимости, для которых поставщиком программного компонента ещё не предоставлена исправленная версия.

Параметр `--exit-code 1` заставляет Trivy возвращать код ошибки при обнаружении уязвимости, соответствующей политике Security Gate.

Jenkins в этом случае останавливает pipeline и не выполняет Deploy.

Логика Security Gate:

    Docker image
         |
         v
    Trivy
         |
         v
    Исправимая HIGH/CRITICAL?
         |
      +--+--+
      |     |
      Да    Нет
      |     |
      v     v
    FAIL   Deploy

## 10. Результат повторного анализа Trivy

После обновления системных компонентов повторный анализ показал:

    Vulnerabilities: 0

для блокирующей проверки в рамках установленной политики.

Таким образом, исправимые HIGH/CRITICAL-уязвимости, соответствующие настроенному Security Gate, обнаружены не были.

Важно учитывать, что используется параметр `--ignore-unfixed`. Поэтому результат 0 означает отсутствие блокирующих уязвимостей в соответствии с установленной политикой, а не гарантированное отсутствие любых существующих уязвимостей.

## 11. Сохранение результатов анализа

Для Trivy настроено автоматическое создание отчёта:

    trivy-report.json

Jenkins сохраняет его как артефакт сборки.

Это позволяет:

- просмотреть результат после завершения pipeline;
- использовать результат для аудита;
- анализировать обнаруженные CVE;
- сравнивать результаты различных сборок.

Таким образом, результаты анализа сохраняются не только в Console Output Jenkins, но и в машиночитаемом формате JSON.

## 12. Выявленные слабые места

Помимо автоматического анализа был выполнен ручной анализ приложения и CI/CD-инфраструктуры.

В результате были выявлены следующие потенциальные слабые места.

### 12.1. Недостаточное ограничение числового ввода

Первоначальная модель запроса использовала:

    a: float
    b: float

без явного ограничения допустимого диапазона и специальных floating-point значений.

Автоматические SAST/SCA-инструменты не обязательно определяют такую проблему, поскольку она относится к логике и контракту API.

### 12.2. Отсутствие Rate Limiting

В текущей реализации отсутствует ограничение количества HTTP-запросов от одного клиента.

Злоумышленник или некорректно работающий клиент потенциально может генерировать большое количество запросов и создавать дополнительную нагрузку на сервис.

В production-среде рекомендуется использовать rate limiting на уровне reverse proxy, API Gateway либо приложения.

### 12.3. Отсутствие ограничения размера HTTP-запроса

Calculator API работает с небольшими JSON-запросами.

Однако в текущей учебной конфигурации не задано отдельное ограничение максимального HTTP request body.

В production такое ограничение рекомендуется устанавливать на уровне reverse proxy или API Gateway.

### 12.4. Доступность Swagger/OpenAPI

FastAPI предоставляет документацию:

    /docs
    /redoc
    /openapi.json

Для учебного приложения это полезно и упрощает тестирование.

В production-среде необходимость публичного доступа к данным endpoint должна определяться моделью угроз и требованиями системы.

При необходимости документация может быть ограничена или отключена.

### 12.5. Доступ Jenkins к Docker Socket

Для сборки и развёртывания контейнера Jenkins использует:

    /var/run/docker.sock

Доступ к Docker socket предоставляет CI-системе значительные полномочия по управлению Docker Engine.

В рамках локального учебного стенда это решение допустимо.

Для production-инфраструктуры предпочтительно использование изолированных Jenkins build agents или специализированных механизмов безопасной сборки контейнеров.

### 12.6. Использование плавающих Docker-тегов

Для некоторых CI-инструментов используются образы:

    aquasec/trivy:latest
    semgrep/semgrep
    alpine

Использование плавающих тегов снижает воспроизводимость CI/CD.

Содержимое такого образа может измениться без изменения исходного Jenkinsfile.

Для production рекомендуется фиксировать конкретные версии:

    image:<version>

или использовать digest:

    image@sha256:<digest>

### 12.7. Устаревание базового Docker-образа

Приложение использует базовый образ:

    FROM python:3.12-slim

Новые CVE могут появляться даже без изменения собственного исходного кода приложения.

Поэтому Docker-образ необходимо регулярно пересобирать, обновлять и повторно проверять Trivy.

## 13. Реализованное усиление валидации входных данных

По результатам ручного анализа в Pydantic-модель были добавлены ограничения числовых параметров.

Вместо:

    a: float
    b: float

используется:

    a: float = Field(
        ge=-1_000_000_000,
        le=1_000_000_000,
        allow_inf_nan=False,
    )

    b: float = Field(
        ge=-1_000_000_000,
        le=1_000_000_000,
        allow_inf_nan=False,
    )

Параметры `ge` и `le` задают нижнюю и верхнюю допустимые границы значений.

Параметр `allow_inf_nan=False` запрещает специальные значения:

    NaN
    +Infinity
    -Infinity

Таким образом, некорректные значения отбрасываются на уровне входной модели до передачи данных в бизнес-логику.

## 14. Обработка деления на ноль

В вычислительном модуле предусмотрена явная проверка:

    if b == 0:
        raise ValueError("Division by zero is not allowed")

Ошибка обрабатывается API-слоем и преобразуется в контролируемый HTTP-ответ.

Это предотвращает неконтролируемое исключение при выполнении операции деления.

## 15. Разделение компонентов приложения

Приложение разделено на функциональные компоненты:

    app/api
    app/schemas
    app/services

`app/schemas` отвечает за валидацию входных и выходных данных.

`app/api` отвечает за HTTP-маршруты и преобразование ошибок в HTTP-ответы.

`app/services` содержит вычислительную бизнес-логику.

Такое разделение уменьшает связанность компонентов и упрощает тестирование, аудит и дальнейший анализ безопасности.

## 16. Безопасность Docker-контейнера

В Dockerfile создаётся отдельный непривилегированный пользователь:

    RUN groupadd -r appgroup && useradd -r -g appgroup appuser

Перед запуском приложения выполняется:

    USER appuser

Таким образом, Calculator API не работает внутри контейнера с правами root.

Это соответствует принципу минимальных привилегий и уменьшает возможные последствия успешной эксплуатации уязвимости приложения.

## 17. Предлагаемое усиление защиты контейнера

Дополнительной мерой может стать запуск production-контейнера с параметрами:

    --read-only
    --security-opt no-new-privileges:true
    --cap-drop ALL

`--read-only` запрещает запись в файловую систему контейнера.

`no-new-privileges` предотвращает получение процессами новых привилегий.

`--cap-drop ALL` удаляет дополнительные Linux capabilities, которые калькулятору для работы не требуются.

## 18. Предлагаемые улучшения

Для дальнейшего повышения безопасности рекомендуется:

1. Реализовать rate limiting.
2. Ограничить максимально допустимый размер HTTP request body.
3. Использовать HTTPS/TLS при публикации API во внешней сети.
4. При необходимости ограничить доступ к Swagger/OpenAPI.
5. Использовать фиксированные версии Docker-образов security-инструментов.
6. Регулярно обновлять базовый Python/Debian image.
7. Регулярно выполнять анализ Python-зависимостей.
8. Использовать изолированные Jenkins build agents.
9. Сохранять результаты security-проверок для последующего аудита.
10. Добавить SBOM (Software Bill of Materials).
11. Добавить автоматический поиск секретов в Git-репозитории.
12. Рассмотреть дополнительное динамическое тестирование API (DAST).

## 19. Ограничения проведённого анализа

Результаты автоматизированного анализа не являются гарантией полного отсутствия уязвимостей.

Semgrep зависит от используемых правил статического анализа и может не обнаружить логические и архитектурные ошибки.

pip-audit обнаруживает известные уязвимости сторонних Python-пакетов, информация о которых присутствует в используемых источниках.

Trivy зависит от актуальности базы уязвимостей и информации, предоставляемой поставщиками пакетов.

Использование `--ignore-unfixed` также означает, что уязвимости без доступного исправления не блокируют развёртывание.

Автоматизированные инструменты не заменяют:

- ручной анализ исходного кода;
- code review;
- моделирование угроз;
- penetration testing;
- анализ production-конфигурации.

## 20. Итоговая оценка

В рамках анализа безопасности Calculator API проверялись:

    Исходный код             -> Semgrep
    Python-зависимости       -> pip-audit
    Docker image             -> Trivy
    Функциональность         -> pytest
    Входные данные           -> Pydantic
    Работоспособность        -> Health Check

Первоначальный анализ Docker-образа выявил 51 уязвимость уровня HIGH в системных компонентах базового образа.

После анализа результатов были обновлены доступные системные пакеты и настроен блокирующий Trivy Security Gate.

Повторная блокирующая проверка не выявила исправимых HIGH/CRITICAL-уязвимостей в рамках установленной политики.

Semgrep не обнаружил известных небезопасных конструкций в исходном коде:

    Findings: 0

pip-audit не обнаружил известных уязвимостей Python-зависимостей:

    No known vulnerabilities found

По результатам ручного анализа дополнительно была усилена валидация числовых параметров API.

Таким образом, реализован многоуровневый подход к анализу безопасности:

    Functional testing
            |
            v
    SAST
            |
            v
    SCA
            |
            v
    Container scanning
            |
            v
    Security Gate
            |
            +------ FAILURE -> Deploy запрещён
            |
            v
          Deploy
            |
            v
       Health Check

Развёртывание новой версии выполняется только после успешного прохождения функциональных и блокирующих security-проверок.
